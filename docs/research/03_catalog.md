# C. Destructive-command catalog

Scope per the brief: a reference catalog of destructive / arbitrary-execution
command forms `guardrails.js` should consider, under the **mistake model**
(Claude writes a bad command by accident), not an adversarial model. Every
family table below splits into a **Baseline** (already enforced today —
listed only for completeness, not proposed) and **Proposed** (a real gap,
with a tier recommendation and legitimate-use reasoning). Findings are
cross-checked against `plugins/bash-guardrails/hooks/guardrails.js` and
`test/run.js` as of this research date (2026-07-02); "already covered" claims
were verified by reading the actual regex, not assumed.

One structural, cross-cutting finding worth stating up front: **DENY_RULES
scan the whole command string, so a destructive Unix command is caught even
behind a pipe or `xargs`** (e.g. `find . | xargs rm -rf` still matches the
`rm -rf` regex). Most of the "family 1" items the brief asks about turn out to
already be non-issues for a different reason: `cp`, `mv`, `rsync`, `ln`,
`shred`, `truncate`, `xargs`, `parallel` are **not** in `ALLOW_COMMANDS` at
all, so they fall to the "ask" tier by default regardless of flags — nothing
to add. The real gaps cluster in three places: (1) git subcommands/flag
spellings not yet matched by `GIT_DENY_RULES`, (2) the ecosystem
package-runner tools (`npx`, `*dlx`) which **are** allow-listed and can fetch
+ execute arbitrary code, and (3) two PowerShell blind spots where the
existing rules check the wrong thing (leading segment only, or `-Force` only).

A comparable open-source project, **`Dicklesworthstone/destructive_command_guard`**
(a Claude-Code-adjacent shell guard with 50+ rule "packs" — DB, containers,
k8s, cloud CLIs, Windows, disk/system, IaC), independently arrived at the same
"catch nested-shell escapes" pattern flagged in family 4 below: it explicitly
detects `python -c '...'`, `bash -c '...'`, and similar indirect execution as
a named technique ("three-tier heredoc architecture"). That's outside
bash-guardrails' current scope (dev-workflow commands, not DB/cloud/k8s CLIs)
but corroborates the nested-interpreter blind spot as a real, previously-seen
class of gap, not a hypothetical. [github.com/Dicklesworthstone/destructive_command_guard](https://github.com/Dicklesworthstone/destructive_command_guard)

## 1. Filesystem

### Baseline (already enforced — not proposed)

| Command form | Enforcement |
|---|---|
| `rm -r` / `rm -rf` / `rm --recursive` (any path, incl. `/bin/rm -rf`) | `DENY_RULES`, path-aware |
| `find ... -delete` | `DENY_RULES` |
| `find ... -exec(dir) rm ...` | `DENY_RULES` |
| `find ... -exec(dir) <anything else>` (e.g. `-exec mv`) | `NEVER_AUTO_ALLOW` → ask |
| `chmod -R` / `chown -R` | `NEVER_AUTO_ALLOW` → ask |
| `xargs ... rm -rf` / `parallel rm -rf` piped from `find` | Already caught — `DENY_RULES` scans the whole string, and `xargs`/`parallel` aren't allow-listed anyway, so this is doubly safe |
| `dd if=...`, `mkfs`, fork bomb `:(){ :|:& };:` | `DENY_RULES` |

## 2. Git data-loss

### Baseline (already enforced — not proposed)

`git push --force`/`-f`/`--force-with-lease`, `git push <remote> main|master`,
`git push --delete`/`-d`, `git push origin :branch`, `git push --mirror`,
`git reset --hard`, `git clean -f` (and `-fd`/`-fdx`/any flag combo containing
`f` — verified the regex `-\S*f` matches any dash-flag *containing* an `f`
character anywhere, not just an exact `-f` token, so `-fdx` is already
covered), `git checkout -- .`, `git branch -D`.

### Proposed

| Command form | Why destructive | Suggested tier | Legitimate-use frequency | Source/citation |
|---|---|---|---|---|
| `git push origin +main` / `+refspec` (force-push via leading `+`, an alternate spelling of `--force` that git accepts on the refspec itself) | Identical effect to `--force` but the regex only looks for `--force`/`-f`/`--force-with-lease` tokens, not a `+` prefix on the refspec | **DENY** — same tier as its `--force` sibling, for consistency; a rewrite (spell out `--force`) costs nothing | Low — `+refspec` is a less-typed, more "power-user golfing" spelling than `--force`; most people/agents write `--force` | [git-scm.com/docs/git-push](https://git-scm.com/docs/git-push) — refspec docs describe leading `+` as forcing the update, equivalent to `--force` for that ref. Confirmed already in the brief's "confirmed holes" list — included here for tier justification, not as a new discovery |
| `git stash drop` / `git stash clear` | Stash entries are dropped with no separate safety net; git-scm's own docs and community sources describe recovery as a manual, best-effort `git fsck --unreachable` grep, not a guaranteed undo | **DENY** — consistent with `git reset --hard`/`git clean -f`, which are already denied despite comparable legitimate-use frequency | Moderate (routine stash hygiene) — but the project already accepts this exact trade-off for `reset --hard`/`clean -f`, so consistency argues for the same tier | [git-scm.com/docs/git-stash](https://git-scm.com/docs/git-stash); recovery-is-fragile characterization corroborated by multiple secondary sources (CoreUI, git-tower) |
| `git restore <path>` / `git restore .` (default target = working tree, discards uncommitted edits) — **excluding** `git restore --staged ...`, which only unstages and does not touch the working tree | Overwrites working-tree file content from the index/HEAD with no confirmation and no separate undo path (unlike a commit, there's no object retained once overwritten) | **DENY** for the working-tree-touching form only; **must not** match `--staged`-only invocations, which are safe/reversible (this is the same false-positive-avoidance discipline the project already applies to `checkout -- .` vs. `checkout <branch> -- <path>`) | High for `git restore <file>` used deliberately; but `checkout -- .` (same effect, older spelling) is already denied at the same frequency profile, so consistency argues for parity | [git-scm.com/docs/git-restore](https://git-scm.com/docs/git-restore) — confirms `.` restores all files in the current directory from index/HEAD to the working tree, and that removal-to-match-source applies when a path is tracked but absent in the source; **no explicit "irreversible" warning is present in the man page itself**, noted as a documentation gap upstream, not something this project can rely on git to warn about |
| `git checkout .` / `git checkout <path>` (bare, no `--` separator — same discard effect as the already-denied `checkout -- .`, just a different spelling) | Same effect as the covered rule; only the `--` is missing | **DENY** — extend the existing pattern to the bare spelling | Same profile as the already-denied form | [git-scm.com/docs/git-checkout](https://git-scm.com/docs/git-checkout) |
| `git switch --discard-changes` / `git switch -f <branch>` | `git switch` is git's newer, docs-recommended replacement for branch-switching `checkout`; `-f`/`--discard-changes` explicitly proceeds even when the working tree/index differ from HEAD, discarding those differences | **DENY** — same class as `checkout -f`/`restore` | Low-moderate — `git switch` itself is newer and less universally used than `checkout`, but its docs actively steer users toward it, so frequency will grow | [git-scm.com/docs/git-switch](https://git-scm.com/docs/git-switch) — `-f` documented as alias for `--discard-changes` |
| `git branch --delete --force` / `-d -f` / `-D` combined with other flags (e.g. `-Dr`) | Same effect as the already-denied `-D`, different spelling; force-deletes a branch even with unmerged commits | **DENY** — extend the existing `-D`-only pattern to cover the spelled-out and combined forms | Same profile as `-D` (common branch cleanup, but unmerged-commit loss risk is real) | [git-scm.com/docs/git-branch](https://git-scm.com/docs/git-branch) — `-D` documented as shorthand for `--delete --force` |
| `git tag -d <tag>` (delete a local tag) | Deletes a local ref; but tags have no dedicated reflog, and a namespace mismatch (deleting the wrong tag) is possible | **Ignore** (leave on default ask/passthrough — no new rule) | High (routine local-tag cleanup) | Lower severity than branch/stash: tags are metadata pointers, commonly re-derivable from the remote (`git fetch --tags`) if the tag was ever pushed; not "work" in the same sense as uncommitted edits or stashes, so it doesn't meet the bar the project already applies |
| `git update-ref -d <ref>` (plumbing-level ref deletion, bypasses `branch -d`'s merge-safety check) | Directly deletes a ref with none of the safety checks `git branch -d` performs (e.g. no "not fully merged" warning) | **ask** (demote, not hard-deny) — add to a git-specific "never auto-allow" style list rather than `GIT_DENY_RULES` | Very low — this is a plumbing command; a human or agent almost never types it directly outside of scripts/tooling, so when it *does* appear it's more likely deliberate/scripted than an accidental mistake, which argues against a hard block | [git-scm.com/docs/git-update-ref](https://git-scm.com/docs/git-update-ref) — **Confirmed currently a silent gap**: `git` is on `ALLOW_COMMANDS` and no existing rule matches `update-ref`, so this auto-approves today |
| `git reflog expire --expire=now --all` / `git reflog delete <entry>` (removes the recovery safety net other operations depend on) | Doesn't destroy live data directly, but forecloses recovery of anything currently only reachable via reflog (e.g. commits orphaned by an earlier `reset --hard`) — compounds the severity of *other* destructive ops | **ask** (demote) — one step removed from live data loss, so full DENY is disproportionate, but silent auto-approval is wrong given how much recovery value it destroys | Very low outside CI/repo-maintenance contexts; docs themselves discourage manual use | [git-scm.com/docs/git-reflog](https://git-scm.com/docs/git-reflog) and Atlassian's reflog tutorial, both characterizing `expire`/`delete` as having "potential for data loss" and "not commonly invoked by end users." **Confirmed currently a silent gap** — `git` leading token is allow-listed, nothing else matches |
| `git gc --prune=now [--aggressive]` (immediately, not after the default 2-week grace window, deletes loose objects unreachable from any ref) | Removes the grace period that protects recently-orphaned-but-still-wanted objects (e.g. from an accidental `reset --hard` moments earlier); concurrent-process corruption risk is also documented | **ask** (demote) — bare `git gc` (no `--prune=now`) is extremely common and benign (routine repo maintenance, sometimes triggered automatically by git itself), so only the `--prune=now`/`--aggressive` combination should be flagged, not `git gc` generically | Low for the `--prune=now` flag specifically; the project's docs themselves recommend against `--aggressive` "almost entirely" | [git-scm.com/docs/git-gc](https://git-scm.com/docs/git-gc); prune-window and concurrency-risk details corroborated by Atlassian's git-gc tutorial and man7.org's git-gc(1). **Confirmed currently a silent gap** |
| `git filter-branch ...` / `git filter-repo ...` (full history rewrite) | Rewrites commit history; object names change, old history becomes unreachable/pruned. `filter-repo`'s own FAQ describes it as intentionally ending with an immediate reflog/object prune, i.e. by design leaves no easy undo | **ask** (demote, not DENY) — nobody types `filter-branch`/`filter-repo` by accident; the command name itself signals deliberate intent. A prompt (not a hard block) respects that while still catching the case where an agent invokes it without the user having explicitly asked for a history rewrite | Low-moderate, but always deliberate when used (e.g. purging a committed secret) | [git-scm.com/docs/git-filter-branch](https://git-scm.com/docs/git-filter-branch) (git project's own docs now steer users to filter-repo instead); [github.com/newren/git-filter-repo FAQ](https://github.com/newren/git-filter-repo/blob/main/Documentation/FAQ.md). **Confirmed currently a silent gap** — both resolve to leading token `git`, which is allow-listed, and no subcommand-specific rule exists |
| `git worktree remove --force` (removes a worktree, including any uncommitted changes inside it, even when "unclean") | `remove` normally refuses an unclean (uncommitted-changes) worktree; `--force` overrides that refusal | **ask** (demote, not DENY) — this project's own agent tooling uses git worktrees as an isolation mechanism (see the `Agent` tool's `isolation: "worktree"` option in this very environment), so legitimate automated use is plausible enough that a hard block would cost real capability, not just create friction | Moderate — meaningfully higher than most rows in this table because worktree-based workflows (including this project's own tooling) routinely need force-removal of scratch worktrees | [git-scm.com/docs/git-worktree](https://git-scm.com/docs/git-worktree) — confirms `remove` refuses an unclean worktree without `--force`, and locked worktrees need `--force` twice. **Confirmed currently a silent gap** |

## 3. Arbitrary-exec reachable through allow-listed tools

This family is different in kind from 1 and 2: the *leading command itself*
is already on `ALLOW_COMMANDS` (`npx`, `npm`, `pnpm`, `yarn`, `bun`, `pip`,
`pip3`, `go`, `cargo`), so nothing in `DENY_RULES`/`BLOCK_RULES` even looks at
these invocations today — the only lever is `NEVER_AUTO_ALLOW`-style
demotion. The project already accepts this exact trade-off for
`node -e`/`python -c`: useful, extremely common, but demoted to ask because
"the deny scan can't see inside an interpreter" (README, "Trade-offs"). The
same logic applies directly to package runners: the leading token (`npx`)
tells you nothing about what code the fetched package will run.

| Command form | Why destructive | Suggested tier | False-friction cost | Source/citation |
|---|---|---|---|---|
| `npx <pkg>` / `npm exec <pkg>` (registry-fetch-and-run, not a locally-declared script) | Fetches and executes an arbitrary, potentially-unpinned package from the registry on every invocation unless `--no-install`/lockfile-pinned; a single compromised or typosquatted package name is full code execution | **ask** (demote via a `NEVER_AUTO_ALLOW`-style pattern on `npx`/`npm exec`) | **Bounded, not a lost capability** — same trade-off already accepted for `node -e`. The safer two-step alternative (install once, then call the local `.bin` directly, or add to `package.json` scripts) remains fully available; this only adds one prompt for the ad-hoc "run something I haven't installed yet" pattern | [socket.dev — npx glossary](https://socket.dev/glossary/npx-npm-package-runner); [aikido.dev — Agent Skills Are Spreading Hallucinated npx Commands](https://www.aikido.dev/blog/agent-skills-spreading-hallucinated-npx-commands) (documents LLM agents specifically being a vector for bad npx invocations — directly on point for this project's threat model). `npx rimraf dist` already listed in the brief as a confirmed hole |
| `pnpm dlx <pkg>` / `yarn dlx <pkg>` / `bun x <pkg>`/`bunx <pkg>` | Same mechanism as `npx`, different package managers | **ask** (same demotion, same reasoning) | Same as above | Search results explicitly note malicious payloads have been executed "via npx, bunx, pnpx, or yarn dlx" as a class — [bastion.tech — npm Supply Chain Attacks 2026](https://bastion.tech/blog/npm-supply-chain-attacks-2026-saas-security-guide) |
| `npm run <script>` / `pnpm run <script>` / `yarn <script>` (running a script **already declared** in this repo's `package.json`) | The script can do anything, but it's not fetching new, unaudited code from the network — it's running whatever the repo's own maintainers already committed | **ALLOW** (no change) — document the trust boundary explicitly, per the brief. This is a different risk shape than `npx`: the code is already inside the repo Claude Code is operating on, no meaningfully-safer two-step alternative exists (you can't "install-then-run" a script that's already local), and demoting it would add friction to nearly every JS test/build/lint invocation | Effectively zero *added* friction is acceptable here since there's no safer rewrite to steer toward — unlike `npx`, demoting this has real lost-capability cost | This is the specific case the brief calls "inherent... probably can't be fully closed" — documenting rather than proposing a rule |
| `npm install` / `pnpm install` / `yarn install` (bare, installing already-declared dependencies) | `preinstall`/`install`/`postinstall` lifecycle scripts execute with the installing user's permissions; GitHub's own supply-chain writeup calls install-time lifecycle scripts "the single largest code-execution surface in the npm ecosystem," and documents real worms (e.g. "Mini Shai-Hulud," Apr–May 2026) propagating via `postinstall` | **ALLOW** (no change) — same "inherent, can't close without losing core capability" bucket as `npm run`; installing declared dependencies is required for nearly all JS development | No safer rewrite exists for "install my dependencies" — this is unavoidable, not a rule gap | [thehackernews.com — GitHub to Disable npm Install Scripts by Default](https://thehackernews.com/2026/06/github-to-disable-npm-install-scripts.html) (npm v12 disabling install scripts by default is itself evidence the ecosystem considers this a real, big-enough risk to fix upstream — meaning **the platform is already closing this gap on its own**, consistent with the "don't build what the platform will do" framing from the sibling ecosystem research) |
| `pnpm install` specifically | Same category, but pnpm has *already* shipped a mitigation: v10 (Jan 2026-era release cadence) blocks dependency build/lifecycle scripts by default, requiring an explicit `allowBuilds` allowlist or `dangerouslyAllowAllBuilds` opt-out | **ALLOW** (no change) — strictly safer than `npm install` today; worth noting as a reason to prefer `pnpm` if this project ever wants to *recommend* a safer default without writing a new rule | N/A | [pnpm.io/supply-chain-security](https://pnpm.io/supply-chain-security); [progosling.com — pnpm 10 now blocks lifecycle scripts by default](https://progosling.com/en/programming-news/pnpm-10-blocks-lifecycle-scripts) |
| `pip install <pkg>` (registry name, e.g. `pip install requests`) | ~1/3 of PyPI packages historically execute code on **download** (before install even completes) via `setup.py`/sdist builds, per academic-adjacent security research | **ALLOW** (no change) — required for nearly all Python development, no safer rewrite for "install a normal registry dependency" | No safer alternative for the common case | [thehackernews.com — PyPI Feature Executes Code Automatically After Package Download](https://thehackernews.com/2022/09/warning-pypi-feature-executes-code.html); [medium.com/ochrona — Arbitrary Code Execution During Python Package Installation](https://medium.com/ochrona/arbitrary-code-execution-during-python-package-installation-3a60990350ef) |
| `pip install <url>` / `pip install git+https://...` (installing from an arbitrary URL or VCS ref, not the registry) | Same code-execution mechanism as above, but the source is an arbitrary URL rather than a named, versioned registry package — a materially different trust level (no registry review/typosquat-namespace protection at all) | **ask** (demote this specific form only) | Lower than bare `pip install` — installing directly from a URL/fork/branch is an occasional, not routine, action; demoting it doesn't block everyday dependency installs | Same sources as above; the URL/VCS distinction is this project's own inference from the general "setup.py executes on install" mechanism, not a separately-cited claim — flagged as reasoning, not a quoted source |
| `go run <pkg>` / `go get`/`go install <remote-pkg>` (build+run of arbitrary Go code, cgo-enabled builds have a history of build-time RCE CVEs) | Multiple CVEs (2018–2024) in `cgo` CFLAGS/LDFLAGS handling allow arbitrary code execution **at build time**, i.e. before the program even runs intentionally | **ALLOW** (no change) — `go run`/`go get`/`go build` are the core Go dev loop; nearly 100% legitimate-use frequency, and distinguishing "safe" from "risky" Go invocations isn't feasible from a leading-token regex | No safer rewrite exists for normal Go development | [github.com/golang/go issue #67119 (CVE-2024-24787)](https://github.com/golang/go/issues/67119); [blog.tempus-ex.com — Go's Recurring Security Problem](https://blog.tempus-ex.com/gos-recurring-security-problem/) (catalogs 7 separate cgo-flag RCE CVEs) |
| `cargo run` / `cargo build` / `cargo install <crate>` (and even `cargo clean`/`cargo update`/`cargo metadata`) | `build.rs` scripts and Cargo config (`[env]`, `rustc-wrapper`, `rustc-workspace-wrapper`, linker config) run arbitrary code on **most** Cargo subcommands, not just `run`/`build` — a security researcher's stated guidance is "do not run any Cargo commands on untrusted projects" | **ALLOW** (no change) — same reasoning as `go run`: core Rust dev loop, ~100% legitimate frequency, and the risk is inherent to *any* Cargo invocation (not just `run`), so demoting only `cargo run` would be both incomplete and disproportionately disruptive | No safer rewrite; demoting only some subcommands would be inconsistent with where the actual risk lives | [shnatsel (Sergey Davidoff) — Do not run any Cargo commands on untrusted projects](https://shnatsel.medium.com/do-not-run-any-cargo-commands-on-untrusted-projects-4c31c89a78d6) — a well-known Rust-security-community post, not an official Cargo doc; treat the specific claim about `[env]`/wrapper-based RCE as **moderately-verified** (single, credible but non-primary source) |

## 4. PowerShell

### Baseline (already enforced — not proposed)

`Remove-Item -Recurse` (any alias), piping into `Remove-Item -Recurse/-Force`,
`Clear-Content`, `Format-Volume`/`Clear-Disk`/`Remove-Partition`/
`Initialize-Disk`/`Reset-PhysicalDisk`, registry key deletion via
`Remove-Item HKLM:\...`, `del`/`rd /s`, `Out-File`/`Set-Content`/
`Add-Content`/`Tee-Object` (steered to Write tool), `New-Item ... -Force`
(ask), the generic mutating-verb list (`Remove-Item`, `Move-Item`,
`Rename-Item`, `Set-Item`, `Set-ItemProperty`, `Set-Content`, `Add-Content`,
`Stop-Process`, `Stop-Service`, `Clear-Item`, `Clear-Content` — always ask,
even non-recursive/non-forced), `Invoke-Expression`/`iex`, `Start-Process`,
web-fetch cmdlets, `ForEach-Object`/scriptblocks, the call operator.

### Proposed

| Command form | Why destructive | Suggested tier | Legitimate-use frequency | Source/citation |
|---|---|---|---|---|
