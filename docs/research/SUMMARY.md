# SUMMARY — bash-guardrails next iteration

Synthesis of `01_ecosystem.md`–`05_telemetry.md` (research date 2026-07-02,
Claude Code v2.1.198). Full findings, tables, and citations live in the
detail files; this is the ranked build order.

Cross-cutting takeaway: the native platform has grown a **real but
undocumented** obfuscation heuristic, an **AST-based** PowerShell permission
matcher, a **gated/paid** LLM "auto mode" classifier, and OS sandboxing that
is **permanently WSL2-only on Windows**. None of it is a zero-cost,
always-on-for-every-user, offline substitute for this hook — but two of
bash-guardrails' current rules (`cat`/`head`/`tail` BLOCK, the whole
PowerShell-rule-*matching* logic) now overlap with things the platform does
better or for free. See `01_ecosystem.md` §1.7 for the full obsoletes table.

## Ranked recommendations

| # | Build | Why now, in this order | Detail |
|---|---|---|---|
| 1 | **Ship the catalog gaps as pure rule additions** — `+refspec` force-push, `git stash drop/clear`, working-tree-discarding `git restore`/bare `checkout`, `git switch -f`, `branch --delete --force` → DENY; `update-ref -d`/`reflog expire`/`gc --prune=now`/`filter-branch`/`worktree remove --force` → new ask-tier list; `npx`/`*dlx`/`npm exec` → ask; PowerShell `New-Item -Value` → BLOCK, interpreter-after-`|` → ask, `Stop-Computer`/`Restart-Computer` → DENY | Zero architecture risk — same regex-array pattern the file already uses, each gap is independently verified against the current source (not assumed), and every item is additive (nothing loosens). Closes essentially all of the brief's "confirmed holes" list in one pass. Do this first because it ships value with the least engineering risk. | `03_catalog.md` §1–4, summary table (14 items) |
| 2 | **Add stable rule ids** to every entry in `DENY_RULES`/`GIT_DENY_RULES`/`BLOCK_RULES`/`NEVER_AUTO_ALLOW` (and PS mirrors), tagged with native tier (`deny`/`block`/`never-auto-allow`) | Free-standing, low-risk refactor with no behavior change — but it's the hard *prerequisite* for both #3 (config) and any future tuning work referencing "which rule fired." Do it right after #1 so the new rules from #1 are born with ids instead of needing a second pass. | `04_config.md` §3 |
| 3 | **Build the hand-rolled quote-aware redactor** (`redactInert`, ~100–150 LOC, zero deps) and mask `BLOCK_RULES`/chain-splitting input through it before the existing regexes run | This is the highest-value architectural fix (kills the quote-blind false-positive class: `cat.png`, `grep "tail"`, backtick-in-commit-message) but is the riskiest of the four to get subtly wrong (nested quotes, `$()` inside double quotes, escapes) — sequence it after the cheap wins (#1–2) so it doesn't block shipping them, and budget real time for the dedicated test corpus the brief and `02_parsing.md` both call for before wiring it in. Note it does **not** fully fix `cat.png`-style false positives on its own — the `cat|head|tail` rule also needs a position/word-boundary tightening (a smaller, separate change). | `02_parsing.md` (full recommendation + migration sketch + failure-mode catalog) |
| 4 | **Ship the two-tier `bash-guardrails.json` config file** (`~/.claude/` + `<project>/.claude/`, `disabledRules`/`ruleOverrides`/`extraAllowCommands`/`extraDenyRules`/`extraBlockRules`), with the fail-safe load path (malformed file → built-in defaults; bad regex → drop that entry only; `ruleOverrides:"off"` on a `deny`-tagged id clamped to `"ask"`) | Depends on #2 (ids). This is the actual "config without forking" ask, and no prior-art project in the ecosystem survey solves it better — worth building because it's genuinely novel value, not because it's cheap. | `04_config.md` §2 (schema + failure matrix) |
| 5 | **Add a small `userConfig` surface in `plugin.json`** (`extra_allow_commands`, `multiple: true`; optional `config_path` file picker) reading `CLAUDE_PLUGIN_OPTION_<KEY>` env vars, feeding the *same* merge function as #4 | Native, shipped since v2.1.83 — do this last as a discoverability on-ramp once the real config engine (#4) exists to feed. Two open GitHub issues suggest it's still a settling feature; treat as supplementary, not load-bearing. | `04_config.md` §4 |
| 6 | **Reconsider the `cat`/`head`/`tail` BLOCK rule** — decide whether to keep it for the Read-tool-steering rationale, narrow it (position-aware, per #3), or drop it | Native Claude Code now free-passes `cat`/`head`/`tail`/`grep`/etc. with zero prompt unconditionally, so the original prompt-avoidance rationale for this rule is largely gone; the remaining rationale (style, avoiding this project's own false positives) is weaker than when the rule was written. Low priority, cheap to defer. | `01_ecosystem.md` §1.1, obsoletes table |

## What NOT to build, and why

| Rejected | Reason | Detail |
|---|---|---|
| Any WASM/native shell parser (`sh-syntax`, `tree-sitter-bash`) as a dependency | Async API mismatch with the hook's synchronous per-process model, unmeasured-but-plausible WASM cold-compile cost on top of an already-tight <100ms budget, and multi-hundred-KB-to-multi-MB payloads that would turn the "readable arrays, edit me" file into a base64 blob with a build step. A 1.1k-star sibling project (`destructive_command_guard`) independently converged on the same regex+span-classification altitude. | `02_parsing.md` comparison table + recommendation |
| Full PowerShell AST parsing via `pwsh -Command` shellout | Confirmed 200–440ms cold `pwsh` start — 2–5× the entire latency budget just to launch the child process, before parsing anything. | `02_parsing.md` PowerShell section |
| An in-hook approximation of Claude Code's own LLM "auto mode" classifier | The platform already ships this for a gated slice of users (Opus/Sonnet 4.6+, plan-restricted) and it costs a model round-trip per action — the opposite of this hook's offline/zero-latency niche. Building a worse version in-repo duplicates a moving platform target instead of the durable gap (every-user, every-plan, offline). | `01_ecosystem.md` §1.4 |
| Reimplementing sandboxing (Seatbelt/bubblewrap equivalent) for Windows | Out of scope for a string-classifying hook; this is an OS-isolation problem Anthropic (or WSL2) owns. Native Windows sandboxing is a durable gap but not one this project can close — flagged as *not inherently permanent* (Codex CLI already ships one), so re-check the roadmap rather than build a workaround. | `01_ecosystem.md` §1.5 |
| A decision-log / telemetry pipeline right now | No prior-art project logs the exact triple needed; log rotation and PII-in-paths are unaddressed gaps industry-wide, not solved problems to copy. More importantly, the feasibility check for the actual goal (measuring which "ask" prompts get approved, to drive auto-allow promotion) came back unresolved: `PostToolUse` carries no decision field, and the more promising `PermissionRequest` hook has no documented way to observe the human's outcome. Building a log without being able to close the loop is premature. | `05_telemetry.md` (explicitly "do not build this now") |
| Copying a competitor's rule set or config schema wholesale | Surveyed 5+ serious community guardrail projects and 4 other agent CLIs — none ships a reusable, engine-agnostic destructive-command classifier or a config schema more capable than what's proposed in #4. Two small techniques *were* worth borrowing (command-start anchoring, heredoc-stripping-before-regex, both from `kylemillerbuilds/agent-guardrails`) and are folded into #2/#3 above rather than listed as a separate build item. | `01_ecosystem.md` §2 |

## Notable findings that don't map to a build item

- **The undocumented native Bash "safety heuristic"** (confirmed real via 6+ open GitHub issues, one open since 2026-03-06 with no maintainer response) is precisely the friction this project exists to route around — its continued existence and lack of a fix is the strongest evidence this project's core value hasn't been obsoleted. `01_ecosystem.md` §1.3.
- **`cmd.exe`/`pwsh`/`bash -c` nested-shell escape hatches are not currently a silent hole** (none of those tokens are allow-listed in either shell's rule set) but should become a **documented, permanent invariant** — never add them to `ALLOW_COMMANDS`/`PS_ALLOW` — rather than something to "fix," since the danger is in the *absence* of a future mistake, not a present gap. `03_catalog.md` item 14.
- **Auto mode's classifier already defaults to blocking most of the git-data-loss holes** this research confirms (`stash drop/clear`, `restore .`, `checkout -- .`, `reset --hard`) for the narrow population that has it enabled — meaning items in recommendation #1 are redundant for that slice of users, but the free/default-mode majority (this project's actual audience) gets none of it. `01_ecosystem.md` §1.4.
